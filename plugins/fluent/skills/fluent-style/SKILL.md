# Fluent Style

Use the canonical Fluent 2.0 `/mcp` profile.

## Read path

- Start broad closet work with `fluent_get_closet_context(domain="style", intent="closet", detail="summary")`.
- For purchase advice, call `fluent_get_closet_context(domain="style", intent="purchase", candidate=...)` once.
- The host inspects candidate images and owns the stylist judgment. Fluent supplies owned closet context, media references, evidence, and completeness. Fluent does not track budgets; for affordability, ask the user.
- Use `fluent_list_closet_items`, `fluent_get_closet_item`, `fluent_list_closet_evidence`, and `fluent_get_closet_item_photos` only when the context packet leaves a specific gap.
- Never claim an image was inspected merely because Fluent returned an image URL.
- For "what should I wear?", "which shoes?", and other owned-item outfit decisions, check the live Fluent closet before naming anything the user owns. List the relevant category, shortlist the plausible saved items, fetch their media with `fluent_get_closet_item_photos`, and actually inspect those images before making visual color, proportion, texture, or silhouette comparisons.
- Do not say "from what I know you own" or imply live closet grounding when no current Fluent read occurred. If media cannot be inspected, give a clearly text-metadata-only answer or ask for the missing visual evidence instead of presenting a visual ranking.
- Respect the live Style profile's closet coverage. `representative` permits saved-closet-wide claims only about the user's current Fluent closet. For `partial`, `out_of_date`, or `unknown`, qualify negative claims as "among the items you have added" or "I do not see this in your current Fluent closet"; never turn missing saved evidence into "you do not own this." Update coverage only after the user explicitly confirms it, using `fluent_update_profile` with `domain="style"`, `kind="closet_coverage"`, `status="confirmed"` or `"corrected"`, and exactly one of `representative`, `partial`, `out_of_date`, or `unknown`.
- Treat `closetFreshness` as an explicit-evidence upkeep boundary, not a timer. Never call a closet stale merely because time passed, never recommend an archived item from memory, and never invent background repair. Mention review or exact-item repair only when the user asks about closet health, an affected saved item is already relevant, or `out_of_date` coverage materially weakens the current answer.
- For "build me an outfit from what I own," enumerate the complete active closet by following every `fluent_list_closet_items` `nextCursor` until it is null. The first page is never proof of the whole closet. Choose 3 to 5 exact active saved IDs, inspect each shortlisted item's media separately, and explain the exact pieces in wearing order. Respect occasion, weather, fit, formality, the current request, and confirmed preferences.
- Render an owned outfit with `fluent_show_closet(filter={item_ids:[EXACT_IDS...]}, presentation={mode:"comparison"})`. Pass only the selected exact IDs; do not substitute a category, retailer product, generic garment, archived record, or remembered item. Offer at most one bounded alternative by naming one exact saved replacement and the selected item it replaces.
- For possible-duplicate review in an MCP Apps host, render exactly the two saved records with `fluent_show_closet(filter={status:"active",item_ids:[EXACT_ID_A,EXACT_ID_B]}, presentation={mode:"comparison"})` and omit `focused_item_id`. Do not say the comparison is open unless that tool returned. Visual similarity never auto-merges records.
- Treat that exact-ID comparison as the first visual outfit board. Modeled imagery is optional: generate it only after an explicit user request and approval of the identity reference, preserve the person's likeness and garment construction, and never attach the generated image to an item or replace its Catalog/Original media. Fluent has no durable look-save tool yet, so do not claim the look was saved.
- Capture natural corrections such as "runs small," "comfortable," "hard to style," "too formal," "rarely worn," or "works well for travel" on the exact saved item through `fluent_record_closet_item_feedback`. Use its typed `feedback` object for wear understanding, feedback signals, works-for, avoid-for, and a concise note; use `fit_assessment` for fit. Set top-level `source="user"` or `"user_correction"`; for user-stated fit, also set `fit_assessment.source` to the same value (an omitted nested source safely inherits that top-level user source). User-stated evidence outranks inference, and silence never means unworn.
- After naming one best owned item, render that exact saved item with `fluent_show_closet(filter={item_ids:[WINNER_ID]}, presentation={mode:"recommendation", focused_item_id:WINNER_ID, recommendation_reason:"CONCISE_REASON"})`. The user-facing payoff is the winning item with its saved media and a concise reason—not the whole closet, a category/subcategory/query filter, or a comparison grid. Reserve `mode="detail"` for an explicit request to inspect or manage the saved item. Render a comparison only when the answer intentionally presents multiple co-equal choices.

## Add photos to an existing item

- Match the supplied photo to the exact existing item; ask only when identity is ambiguous. Call `fluent_add_closet_item_photo` with `image_type="fit"` for a worn photo or `"alternate"` for product/detail evidence. Inspect and retain the original. Do not use a primary or replacement write for an add request. Send the real photo (a file, real image bytes, or a direct image URL); never pass an app-internal image handle such as a code-mode image reference, which Fluent rejects without saving.
- Verify the returned `photoId` in the same item's readback. Adding photos preserves the cover and prior photos. `fluent_set_closet_item_photo` replaces a role slot (for example the primary cover), so never use it for an add request.
- Change an existing cover only when requested: inspect retained source evidence, prepare and review the candidate using the rules below, then save approved owned Catalog bytes with the exact source photo ID. Keep the current cover until the candidate is ready. If the item has no cover, prepare one from the new source when suitable; never invent a garment from a label/detail-only photo.

## Import from photos, files, or folders

- Treat the host model as the only vision owner. Use its available filesystem, media, image, and reasoning capabilities to inspect the supplied collection; Fluent validates, stores, and renders the result rather than running a second visual interpretation.
- Inspect original-resolution sources in bounded batches rather than sampling the folder or downscaling before extraction. Use only the file and image capabilities available in the current host. For HEIC or another format the host cannot inspect directly, convert it to a full-resolution JPEG/PNG derivative when the host supports that, inspect the derivative, and keep the source unchanged; otherwise ask for a supported image upload. Never claim a conversion or inspection that did not happen, and never persist a local path.
- Use the currently projected Fluent tool schemas as the authoritative write contract; do not depend on an unlisted guidance resource.
- Consider the source collection together. Associate complementary product, worn, label, and detail views with the same physical garment when the evidence supports it.
- When photos contain multiple people, import garments only from the target person. Infer the target without interruption when one recurring person is unambiguous; otherwise ask once for clear target-person references or for the user to identify themselves in a source photo. Hold uncertain matches rather than importing another person's clothing.
- Keep target-person references local and scoped to the current import. Do not persist them, face embeddings, or an identity profile in Fluent, and do not reuse them for modeled or on-person generation without separate user intent.
- Preserve source files unchanged. Create one item per distinct owned garment, except an established pair such as shoes. Prefer omission over invented branding, text, construction, color, material, or identity, and hold an item when faithful recovery would require substantial invention.
- Prefer a verified original retailer product photo over regenerating the garment. Once the exact product and colour are confirmed, select a complete, clear product view with consistent orientation (shoe toes facing right where a verified source view is available; never mirror lettering or logos); use existing transparency directly and normalize its framing without changing proportions. For an opaque clean product photo, prefer a reviewed background-only alpha mask that preserves garment pixels. Keep the untouched original separately, label the masked derivative as Catalog rather than generated or original evidence, and retain its source association. Generate a faithful product view only when the available source cannot supply a usable complete product view. Inspect edges, soles, logos and text on light and dark backgrounds before accepting either approach. Never use generated imagery as independent identity evidence.
- For sources that need isolation, use the host's image editor to produce a faithful, complete garment cutout and use the accepted result as the primary Catalog image. Request actual transparency, no exterior cast shadow, and comfortable padding; preserve the original product or worn photo separately. A clean product photo may instead use a reviewed alpha mask that preserves its garment pixels. Do not require generative reconstruction when the source already supplies the complete garment.
- Before declaring `background_removed=true`, verify the saved output has a real alpha channel and transparent exterior, then inspect it on both light and charcoal backgrounds at useful item size and close-up. Reject baked checkerboards, white/chroma fringes, clipped hems or soles, altered logos/text and invented construction. Transparent corners alone are insufficient. Use supported background cleanup or regenerate a failed cutout, then repeat the review; never conceal defects by recoloring the garment with CSS. Keep the source as the evidence and label generated imagery as generated.
- A direct request to import the supplied collection is explicit approval for that scoped batch. Use a stable `client_token` per physical item and one shared `batch_id`; do not ask for confirmation item by item.
- Let Fluent surface possible duplicate candidates, but decide sameness only from source evidence. `fluent_add_closet_item` only creates. For a different garment, resend with `on_duplicate="force"` plus that candidate ID to keep both with the distinction recorded. For the same garment, do not create it: attach the inspected photo to the existing item with `fluent_add_closet_item_photo` (or `fluent_set_closet_item_photo` with `image_type="primary"` when it has no photo yet). Hold uncertain matches rather than silently dropping or duplicating a garment.
- If the user later confirms two saved closet records are the same physical garment, call `fluent_merge_closet_items` with the redundant exact `item_id`, the canonical exact `merge_into_item_id`, and a new `merge_operation_id`. This keeps one active item and combines their distinct photos; never infer or auto-merge. To undo a merge the user regrets, call `fluent_undo_closet_item_merge` with the archived item's ID and the exact `merge_id` (its `duplicateMergeId`).
- When the user asks in an ordinary chat turn to repair an exact existing closet item, treat that turn as approval for that item only. Read the exact item, then call `fluent_get_closet_item_photos` for that exact item with `purpose="catalog_repair_source"`; inspect the returned retained source evidence, create or select a faithful Catalog image when possible, save it with provenance, and verify the updated item before answering. Never use the current/default Catalog presentation or another generated Catalog image as its own repair source. If the user only asks to view or review the item, do not mutate. Do not change another item, invent unavailable visual evidence, or direct the user to a widget normalization control.
- Create an item once its metadata and duplicate decision are ready. A photo is optional but strongly encouraged: when the host has inspected a suitable product image or faithfully generated one from source evidence, call `fluent_add_closet_item` with `catalog_ready=true`. For an inspected clean source, prefer `image_file`, or pass its exact direct public HTTPS image as `image_url`, with `image_origin="user_source"`; Fluent copies and validates the bytes before atomically storing it as both Catalog and exact source evidence. For a faithful generated Catalog, pass the generated result as `image_file`, the exact retained original/on-you evidence as `source_image_file`, `image_origin="host_generated"`, and `source_image_type="fit"` when appropriate. Fluent derives and binds the stored media identities and hashes. With no usable image (for example a text-only description), save the item without a photo; the result returns `photoStatus: "needs_photo"`, so offer once to add a photo with `fluent_set_closet_item_photo` (the first photo becomes the cover). Never promise a later widget normalization step.
- Prefer owned media for Catalog-ready writes: in ChatGPT, use the native `image_file` and, when generated, `source_image_file` parameters. When the exact inspected image already exists at a direct public HTTPS image URL, `image_url` is also valid because Fluent copies, validates, hashes, and owns those bytes before commit. Do not copy local workspace paths, pass a product page/gallery URL, or scrape browser DOM URLs. Other hosts may also pass bounded full-resolution JPEG/PNG/WebP data URLs or approved temporary hosted-file URLs when their projected tool contract supports them. Never echo inline bytes or temporary bearer URLs in the user response.
- Finish the ordinary user turn with a concise imported/held/possible-duplicate summary. Created items are `active`. In UI-capable hosts, a successful create result presents the exact saved item directly in the Closet app; do not call `fluent_show_closet` again merely to complete the normal review. In text-only or non-UI hosts, follow the returned `reviewHandoff` exactly with `filter.status="active"`, its exact `filter.item_ids`, `presentation.mode="ingestion_review"`, and exact `presentation.focused_item_id`. `pending_review` is not a lifecycle or render-filter status. Keep manifests, batching, retries, checkpoints, and other operational mechanics out of the user-facing response unless they materially block completion.

## Write path

- `fluent_add_closet_item`: explicit, user-approved onboarding of a newly owned item. Dresses, jumpsuits, rompers and overalls use category `ONE_PIECE` (shown as Dresses & jumpsuits).
- `fluent_update_closet_item`: sparse details for an existing item. It does not restore items or change photos or product references.
- `fluent_restore_closet_item`: return an archived item to the active closet (not for undoing a merge).
- `fluent_add_closet_item_photo`: add another original product, detail or fit photo; the cover and saved photos are kept.
- `fluent_set_closet_item_cover`, `fluent_reorder_closet_item_photos`, `fluent_hide_closet_item_photo`, `fluent_replace_closet_item_photo`, `fluent_undo_closet_item_photo_change`: one tool per change to an existing item's saved photos.
- `fluent_merge_closet_items`: combine a user-confirmed duplicate into the item that stays.
- `fluent_save_closet_item_product_details`: a host-researched product reference with attributed facts for an existing item.
- `fluent_undo_closet_item_merge`: undo one duplicate combine with its exact merge cycle.
- `fluent_record_closet_item_feedback`: user/host evidence refresh for an existing item.
- `fluent_set_closet_item_photo`: a host-inspected image for an existing item. To finish an existing generated Catalog repair in one turn, send the generated owned bytes with `catalog_ready=true` and the exact retained `source_photo_id`; do not send the user into a widget normalization loop.
- `fluent_archive_closet_item`: explicit no-longer-owned disposition.
- `fluent_update_profile(domain="style")`: durable style facts the user states, one per call: `size_note`, `fit_preference`, `style_aesthetic`, `style_avoid`, `preferred_store`, `price_band`. Save them in Fluent, not only in host memory. To forget one, send the same kind and value with `status="rejected"`.

Use `fluent_show_closet` only for owned closet viewing/management or model-selected owned comparators when the host supports MCP Apps. The prose purchase judgment leads.

Fluent does not extract arbitrary product pages, scrape retailers, operate browsers, score purchases server-side, or expose earlier Style purchase widgets/tools. Require explicit approval and returned read-after-write proof for every mutation.

A linked closet record can remain as historical evidence after archival. Check closet_item.status and item_available before treating it as available to wear; item_exists means only that the historical record still exists.

### Saved photo library edits

For an explicit request to remove, reorder or select a cover, first render the exact saved item. Call the one tool for the change (`fluent_set_closet_item_cover`, `fluent_reorder_closet_item_photos`, `fluent_hide_closet_item_photo`, `fluent_replace_closet_item_photo` or `fluent_undo_closet_item_photo_change`) with the item ID, `expected_revision` and `operation_id`. Use the exact `photoRevision` and photo IDs returned by the render, and a unique operation UUID. Removal hides retained media; it never deletes source files. Hiding the cover requires `next_cover_photo_id`: a replacement product-photo ID, or `null` for no cover. Fit photos cannot be covers. Undo requires the returned token and unchanged current revision; do not retry a stale change against a newly fetched revision without reviewing it. Verify the returned operation ID and revision, then render the same item to confirm. Photo order/visibility are presentation choices; retained source evidence remains available for model reference.

### Product references
When the host exposes `fluent_save_closet_item_product_details`, read the item first, then submit a typed `reference` with the returned `productReference.revision` (0 if absent) as `expected_revision`, a new UUID `operation_id`, and attributed facts. Save new items first and enrich their returned IDs. A reference replaces its previous version: preserve unchanged facts. Do not use tags or personal fit notes for composition/care.
The host owns retailer research. If the user shares a narrowly relevant receipt, use only its product facts; Fluent never reads email. Send only product facts, not raw receipts, order IDs, addresses, payment details or private links. No connector access is a normal partial outcome. Do not imply background work continues after the host turn.
Ask once for an ambiguous product match; a confirmed match permits listing facts without per-field questions. Preserve rejected matches, and ask before replacing conflicting confirmed information. Use `candidate` for unresolved matches, `confirmed` for user-confirmed/exact-code/receipt matches, and `rejected` for a rejected candidate. Sources identify where each fact came from, independently of who confirmed identity.
Product references never alter the owned size, personal fit or media. Add inspected retailer photos separately through `fluent_add_closet_item_photo` with `image_type: alternate`, preserving the current cover.
